# Feature feasibility: the 30 desktop UI ideas

Reviewed on **2026-09-27** against the current Saturn source. The pasted comparison is background material, not a requirement to implement every Qt feature. This assessment is engineering judgment for a small Python desktop framework; effort and priority are estimates, not delivery promises.

## Practical conclusion

The most useful immediate work is to stabilize the features already present: native windows and DPI changes, keyboard/focus/IME, fonts, control parameters, and rendering regressions. Settings screens can already use `Subpage`; advanced procedural backgrounds can use `Shader`. A full model/view framework, plugin loader, or visual designer would add substantial maintenance before helping ordinary settings and launcher applications.

Keep the existing `ListView`. Its exact measurement, width caches, fixed `item_extent` path, and paint culling are already useful. Unknown wrapping heights still require an initial scan. Consider a small data adapter only when a measured workload needs fewer live controls; a new `VirtualStudentList` or replacement widget hierarchy is not a prerequisite.

**Effort:** S = a local helper or contained API addition; M = several interacting modules plus tests; L = a subsystem, significant native integration, or platform-specific work. These labels are relative engineering effort, not calendar estimates.

**Priority:** now = useful for current desktop correctness; when needed = implement for a concrete application requirement; defer = unlikely to justify its maintenance at the current scope.

## Boundaries that matter for current applications

### Settings and navigation

Use [Subpage](../saturn/subpage.py) for an owned native settings/about/editor window. Each child has its own Page and renderer while sharing one application event loop and route state. Hide/show preserves controls; closing destroys descendants. The route handler decides what to display. These are same-process windows, without a web navigation stack.

### Effects and graphics

[Shader](../saturn/widgets/shader.py) paints a procedural rectangle using built-in effects or user GLSL on the GPU backends, with includes, scalar/vector uniforms, cached compilation and error recovery. Software uses a static fallback color. The Orb Aurora/glass example demonstrates a practical single-pass WGSL-to-GLSL adaptation. `Container.blur` backdrop Gaussian blur is implemented for software (downscaled `pygame.transform.gaussian_blur`) and OpenGL (separable `Renderer.backdrop_blur`). Sampling other controls and multipass particle pipelines still require broader render-target/texture ownership APIs. Raw `page.renderer.context` access is backend-specific integration.

Qt Shader Tools has a shader preparation/pipeline role across graphics APIs. Matching that scope would require shader translation, reflection, resource binding, and backend-specific lifetime work, substantially beyond adding a few useful effects. See the [official Qt Shader Tools overview](https://doc.qt.io/qt-6/qtshadertools-overview.html).

### Data-heavy tools

Model/view separation helps reuse data across item views and gives delegates a defined rendering/editing role. Qt's architecture is described in its [official Model/View guide](https://doc.qt.io/qt-6/model-view-programming.html). That does not make the same abstraction an immediate requirement for a launcher or settings panel.

For Saturn, first measure the existing list. Use known row heights or `item_extent` where valid, avoid rebuilding unchanged control trees, and add a compact data adapter only when object count or update cost is proven to be the limiting factor. Tables, trees, file watchers, proxy sorting/filtering, and editor delegates are distinct features with distinct requirements.

### Native integration and accessibility

Window handles, taskbar progress/badges, native file pickers, text clipboard operations, focus traversal, and IME are already implemented in their documented scope. Native menu bars, system tray, rich clipboard formats, outgoing OS drag, and multiple native windows are still separate work.

Accessible labels alone do not connect an application to a screen reader. Qt describes platform accessibility interfaces and their application-facing infrastructure in its [official accessibility documentation](https://doc.qt.io/qt-6/accessible.html). Saturn needs an actual platform provider and verification with assistive tools before claiming that capability.

## Recommended order

1. **Keep current behavior reliable:** control parameter regressions, caret/selection/IME, native close/resize, fonts, renderer effects, and Subpage lifecycle.
2. **Verify packaging and real DPI migration:** a built distribution, changed working directory, mixed-scale monitor movement, and renderer screenshots.
3. **Add small desktop helpers when they reduce application code:** scoped shortcuts, public text clipboard, file-drop events, and a rendered context menu.
4. **Build data controls from concrete workloads:** a modest table or a flattened expandable tree first; add a model layer only when measured scale or reuse requires it.
5. **Design larger native subsystems for an explicit product target:** tray, multi-window ownership, accessibility provider, or another OS adapter.
6. **Defer infrastructure without users:** general plugin discovery, a visual designer, and arbitrary portable shader toolchains.
